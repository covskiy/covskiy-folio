# План рефакторинга бота

Ветка `refactor/bot-architecture`. Статус: **выполнен** — правки закоммичены
(реорганизация в `bot/` — коммит `c307d74`), документ сохранён как история
решений и исходных сценариев. Пуш в удалённый репозиторий — только после
локальной проверки всего владельцем.

## Цель

Полная переделка бота, начиная с процесса irl: сначала сценарии (раздел
«Процесс irl»), затем архитектура под них — с учётом ограничений бесплатного
тарифа Vercel.

## Решения владельца

1. Скоуп — весь бот: мозг (промт + справка), память диалога, контент-процесс,
   UX чата на сайте.
2. Память диалога — Upstash Redis (free tier, REST API). TTL истории — 24 часа,
   в промт идёт последние 10 сообщений.
3. Контент-процесс — гибрид: файлы в репо — источник истины; админ-маршрут —
   только просмотр/диагностика, не правка.
4. Telegram: Q&A + команды (/help, /reset, /about) + inline-кнопки-подсказки.
   Проактивных сообщений нет. Проксирование сообщений владельцу не делаем,
   `OWNER_CHAT_ID` не нужен: контакты бот выдаёт из справки (элемент
   «Как связаться»).
5. Справка переезжает из TS в JSON (структура {title, text}); промт — в md.

## Процесс irl

### A. Посетитель сайта (вебчат)

1. Открывает сайт — виджет свёрнут (как сейчас).
2. Разворачивает: приветствие + чипсы-подсказки (первые 3 элемента справки).
3. Задаёт вопрос → `POST /api/chat {sessionId, text}` (клиент шлёт только
   текст; sessionId из localStorage).
4. Сервер: история чата из Redis (`chat:web:{sessionId}`, TTL 24ч) → +вопрос →
   `brain.answer()` → сохранить пару вопрос/ответ → `{text, mode}`.
5. Виджет рендерит ответ; `mode=dumb` — бейдж «офлайн-справка».
6. Кнопка «новый диалог»: новый sessionId; старый ключ истечёт по TTL.
7. Чипсы доставляются через GET `/api/chat` (сейчас smoke `{ok, service}` —
   расширяем ответом `{chips: [...]}`).

### B. Пользователь Telegram

1. `/start` — приветствие + inline-кнопки с подсказками вопросов.
2. Свободный текст → история чата из Redis (`chat:tg:{chatId}`, TTL 24ч,
   в промт последние 10) → `brain.answer()` → сохранить → `sendMessage`.
3. Команды: `/help` (что умеет), `/reset` (очистить историю чата), `/about`
   (из справки). Состояния не требуют.
4. Кнопки: `callback_query` с `callback_data = "ask:{n}"` — лимит Telegram
   64 байта на callback_data, поэтому кнопка несёт индекс, вопрос берётся из
   справки по номеру. Ответ через `answerCallbackQuery` + `sendMessage`.
   Состояний нет — Redis хранит только историю диалогов.
5. `allowed_updates: ["message", "callback_query"]` (правка админ-маршрута).
6. На «как связаться» бот отвечает из справки — без сценариев и проксирования.

### C. Владелец

1. Справка — правка `bot/brain/knowledge.json`; промт — правка `bot/brain/prompts/*.md`.
   Всё под git, источник истины — файлы.
2. Пуш в `main` → деплой → оба канала обновились. Проверка до мерджа — на
   preview-ветке.
3. Диагностика — админ-маршрут (просмотр, секрет-заголовок): health (ping LLM,
   ping Redis, getWebhookInfo) + просмотр собранного system prompt.
4. Мониторинг — логи Vercel.

## Архитектура

### Требования → механизм

| Требование                      | Механизм                                                                           |
| ------------------------------- | ---------------------------------------------------------------------------------- |
| Общая память диалога (web + tg) | `bot/store.ts` — обёртка Upstash Redis REST (fetch)                                |
| Отказ хранилища не ломает бота  | fail-open: Redis недоступен → stateless-режим (только текущий вопрос)              |
| История                         | ключи `chat:web:{sessionId}` / `chat:tg:{chatId}`, TTL 24ч, в промт — 10 сообщений |
| Кнопки-подсказки                | `ask:{n}` → вопрос из справки; чипсы сайта — первые 3 элемента JSON                |
| Команды TG                      | разбор в обработчике webhook, без состояния                                        |
| Просмотр промта/health          | расширение админ-маршрута, только GET, секрет-заголовок                            |
| Провайдер LLM                   | без изменений: OpenAI-совместимый endpoint, env                                    |

Один Vercel Function сохраняется (`api/bot.ts` + rewrites): новых публичных
маршрутов нет, callback_query приходит через существующий `/api/telegram`.

### Структура bot/ и сборка system prompt

```
bot/brain/prompts/00-persona.md   — роль, тон
bot/brain/prompts/10-rules.md     — правила ответа
bot/brain/prompts/20-knowledge.md — каркас секции справки, плейсхолдер {{KNOWLEDGE}}
bot/brain/knowledge.json          — знания структурой {title, text}: dumb-режим и чипсы-подсказки
bot/brain/prompt.ts               — сборщик
```

Сборщик — паттерн проверен трейсером (@vercel/nft) и нативным ESM-рантаймом:

```ts
import { readFileSync } from "node:fs";

// Знания — bot/brain/knowledge.json: тот же fs-паттерн с литеральным путём,
// без import-атрибутов (и их рисков на трансляторе облака).
const KNOWLEDGE: { title: string; text: string }[] = JSON.parse(
  readFileSync(new URL("./knowledge.json", import.meta.url), "utf8"),
);

// Порядок в массиве = порядок секций в промте.
// Цифровые префиксы имён — для человека, порядок решает код.
const PARTS = [
  new URL("./prompts/00-persona.md", import.meta.url),
  new URL("./prompts/10-rules.md", import.meta.url),
  new URL("./prompts/20-knowledge.md", import.meta.url),
] as const;

let cached: string | undefined;

export function systemPrompt(): string {
  cached ??= PARTS.map((url) => readFileSync(url, "utf8").trim())
    .join("\n\n")
    .replace(
      "{{KNOWLEDGE}}",
      KNOWLEDGE.map((item) => `## ${item.title}\n${item.text}`).join("\n\n"),
    );
  return cached;
}
```

Жизненный цикл: контент вшивается в артефакт на деплое (как и env); md — это
готовый текст секции промта, без парсинга, единственная обработка — `trim()` и
строковая подстановка `{{KNOWLEDGE}}`; чтение с локального диска лямбды — один
раз на тёплый инстанс (`cached ??=`), не на каждый запрос. Правка промта =
пуш → деплой (как сейчас с knowledge.ts). Если понадобится правка промта без
деплоя — отдельная история (Blob/KV-хранилище), не в этой итерации.

Если md-файл затрейсится неудачно, падение произойдёт внутри `askLlm` →
`brain.answer()` уйдёт в dumb-режим: сайт продолжит отвечать, в логах будет
`ENOENT`.

## Факты платформы (проверено экспериментально)

### Как собираются артефакты

- Статика: Vercel детектит Vite → `vite build` → `dist/` уезжает на CDN. Корень
  репо на проде не раздаётся.
- Функция: каждый файл в корневом `api/` = отдельная функция. Билдер
  `@vercel/node` компилирует TS→JS (typescript + babel) и трейсит граф импортов
  (`@vercel/nft`, node-file-trace) в артефакт функции. Это не склейка в один
  js-файл: артефакт — набор модулей, рантайм грузит их нативным Node-лоадером
  (отсюда обязательность `.js`-расширений в относительных импортах).
- Rewrite в `vercel.json` меняет доставку, а не URL: функция видит исходный
  pathname (`/api/chat`, а не `/api/bot`) — иначе switch в `api/bot.ts` не
  работал бы. Тело запроса, заголовки (в т.ч. secret-token) и query проходят
  без изменений.
- Явный список rewrites (текущий) vs catch-all `/api/(.*)`: с явным списком
  мусорные `/api/*` умирают платформенным 404, функция не вызывается и не будит
  холодный инстанс.

### Ветви, превью и деплои

- Prod-деплой — только пуш в `main`. Пуш в другую ветку по умолчанию создаёт
  preview-деплой: commit-URL (новый на каждый пуш) + стабильный branch-URL
  `<project>-git-<branch>-<scope>.vercel.app`. Кастомный домен к превью
  автоматически не привязывается; превью отдают `noindex`.
- Отключить превью-сборки: дашборд Settings → Build and Deployment →
  Ignored Build Step → «Only build production» (деплой создаётся и сразу
  отменяется: билд-минуты не тратятся, суточный лимит деплоев — да). Точечный
  вариант — `vercel.json`: `"git": {"deploymentEnabled": {"refactor-*": false}}`
  (но конфиг уедет в `main` вместе с мержем ветки).
- Telegram-вебхук один на бота: тест бота на preview-URL через
  `/api/telegram-setup` перекидывает вебхук с прода; после теста вернуть назад.

### Что попадает в артефакт функции (эксперименты с nodeFileTrace)

| Паттерн                                                                       | Трейсится |
| ----------------------------------------------------------------------------- | --------- |
| `readFileSync(new URL("./x.md", import.meta.url), "utf8")` — литерал в вызове | да        |
| Хелпер `read(url) = readFileSync(url, …)`, литерал в месте вызова хелпера     | да        |
| Массив литеральных `new URL(...)` + `map(readFileSync)`                       | да        |
| Путь собран через промежуточные переменные                                    | нет       |
| Путь из `process.env` / параметров рантайма                                   | нет       |

- Правило: путь — литерал относительно импортирующего модуля. `readdirSync` и
  glob-листинги не трейсятся: файлы, не упомянутые литералом, в артефакт не
  уедут (локально такой код работает, в облаке — ENOENT).
- JSON-импорт с `with { type: "json" }` — не нужен: knowledge.json читается
  fs-литералом + JSON.parse (паттерн из таблицы выше), рисков транслятора
  облака нет.
- Статику `dist/` функция не видит (она на CDN, не в лямбде). Данные для
  функции — в её артефакте (импорт/fs-литерал) или через fetch на свой домен.

### Локальные грабли этой машины (Windows)

- `vercel build` и `vercel dev` (CLI 65.10.0) падают: `EPERM: symlink` в кэше
  билдеров (`builders-vlt`) — Windows Developer Mode выключен, неэлевированный
  процесс не создаёт symlinks. Лечение: включить Developer Mode (Параметры →
  Для разработчиков) или элевировать терминал. Это отдельный грабль, не тот,
  что описан в [architecture.md](../docs/architecture.md) (`EISDIR` на
  виртуальных дисках ImDisk).
- Замена `vercel dev` — dev-адаптер функции (шаг 3 плана работ): небольшой
  node-скрипт, оборачивающий `default.fetch` в node:http.
- Симуляция из [local-dev.md](../docs/local-dev.md) компилирует только `.js` —
  md/json за ней не идут; перед запуском вручную копировать контент в `.tmp/sim`
  (см. «Проверки до пуша»).

## План работ (одна задача рефакторинга, шаги в порядке исполнения)

1. **Контент и промт**: `bot/brain/prompts/00-persona.md`, `10-rules.md`,
   `20-knowledge.md`; `bot/brain/knowledge.json` (перенос справки из TS);
   `bot/brain/prompt.ts` (сборщик по разделу «Архитектура»); обновить `bot/brain/brain.ts`.
2. **Хранилище**: `bot/store.ts` — get/set/del + история диалога, fail-open;
   обновить `.env.example` (UPSTASH_*-плейсхолдеры).
3. **Локальный dev-адаптер функции**: небольшой node-скрипт (вне `api/`,
   не деплоится), оборачивающий `default.fetch` в node:http — замена
   сломанного `vercel dev`; vite proxy уже настроен на 3000.
4. **Вебчат**: sessionId, серверная история вместо localStorage-истории;
   правки `src/chat/chat-api.ts` и `chat-widget.ts`; расширить GET `/api/chat`.
5. **Telegram: история и команды**: обработка `/help` `/reset` `/about`,
   контекст через store.
6. **Telegram: кнопки**: telegram-api += reply_markup / answerCallbackQuery /
   editMessageText; callback_query в webhook; `allowed_updates` в админ-маршруте.
7. **Админ-маршрут**: health (LLM ping, Redis ping, webhook info) + просмотр
   промта. Только GET.
8. **Тесты и статика кода**: обновить `bot/tests/` (моки fetch покрывают store,
   сценарии кнопок, fail-open); lint/typecheck/format.
9. **Документация и деплой**: обновить `docs/architecture.md` под новую
   схему; локальная проверка владельцем; деплой preview на этой ветке;
   проверка бота на preview; merge в `main`.

Обоснование порядка: шаг 1 не зависит от хранилища; 2 — фундамент для 4–6;
3 стоит до 4, чтобы весь дальнейший функционал проверялся локально без деплоя.

## Upstash Redis: действия вне возможностей агента

Значения REST URL/TOKEN — секреты: в чат их не присылать, вводить самому в
терминале или дашборде.

**Вариант 1 — Vercel Marketplace (предпочтительно; отдельная регистрация в
Upstash обычно не нужна, всё провижинится через Vercel):**

1. Дашборд Vercel → проект `covskiy-folio` → вкладка **Storage** →
   **Create Database** → выбрать **Upstash Redis**.
2. План **Free**; регион — ближайший к региону функции Vercel (обычно iad1 /
   us-east).
3. Привязать базу к проекту: переменные `UPSTASH_REDIS_REST_URL` и
   `UPSTASH_REDIS_REST_TOKEN` создадутся в окружениях автоматически.
4. Сделать **Redeploy** (env запекается в деплой — грабля выше).
5. Локально подтянуть: `npx vercel env pull .env.local` (команда перезапишет
   файл — свои локальные правки вносить после).

**Вариант 2 — прямая регистрация Upstash (если marketplace не подошёл):**

1. upstash.com → Sign Up (email/GitHub).
2. Console → Create Database → регион как выше; REST API включён по умолчанию.
3. Скопировать из деталей базы REST URL и TOKEN.
4. В терминале проекта (значения вводишь сам, vercel env add спросит их
   интерактивно):

   ```bash
   npx vercel env add UPSTASH_REDIS_REST_URL production
   npx vercel env add UPSTASH_REDIS_REST_URL preview
   npx vercel env add UPSTASH_REDIS_REST_URL development
   # то же для UPSTASH_REDIS_REST_TOKEN
   ```

5. Redeploy; затем `npx vercel env pull .env.local`.
