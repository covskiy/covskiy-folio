# 02 — Telegram-вебхук и развязка зависимостей в `bot/`

Статус: **реализовано (основной объём)** — итоги и отступления от плана в §19.
Ветка: `refactor/bot-architecture` (решение владельца — работать в ней, без
отдельной `refactor/bot-di`).

Документ состоит из двух независимых линий работ:

- **Часть I — Telegram** (§1–§7): поведенческие правки вебхука. Маленькие,
  низкий риск, можно шипить первыми.
- **Часть II — архитектура** (§8–§13): развязка транспорта и домена, контракты
  и composition root. Без переписывания на классы (обоснование — §8).

## Решения владельца (зафиксированы)

1. **Ack — `ack-after`**: сначала обработка (LLM → `sendMessage`), потом
   HTTP `200`. `waitUntil` и `@vercel/functions` не вводим, новых зависимостей
   нет. Вариант ack-first рассмотрен и отклонён — §2, §6.5.
2. **Telegram: отправка → запись истории.** Вебчат — без смены порядка:
   в serverless запись после `return` невозможна без `waitUntil` (§5).
3. **Composition root и контракты (порты) включены** в объём работ (§13).
4. **Классы не вводим**: фабрики + явные зависимости. Когда ООП станет
   оправданным — §8.

---

## 0. Инварианты (что не должно измениться ни при каких правках)

1. Одна Vercel Function `api/bot.ts`, роутинг по `pathname` через rewrites.
2. Публичный HTTP-контракт: коды `200/400/401/403/404/405/429/502`,
   форма `{ ok, text?, mode?, error? }`.
3. Fail-open по store: Redis недоступен → бот отвечает без истории и без
   лимитера, а не падает.
4. Env-имена и их семейства (`UPSTASH_REDIS_REST_*` / `KV_REST_API_*`), TTL 24 ч,
   капы 20 сообщений / 4000 символов, `HISTORY_WINDOW = 10`.
5. Троттлинг warn'ов и четыре ключа деградации (`no-env`, `network`,
   `rest-status`, `rest-error`) — в логах не должно появиться больше шума.
6. Никаких новых **runtime**-зависимостей.
7. Относительные импорты — только с `.js`; `process` — только через
   `import process from "node:process"`; серверный код вне `api/`.
8. Тесты не ходят в сеть.

# Часть I. Telegram-вебхук

## 1. Текущее состояние (для контекста)

Поток «сообщение»: секрет → JSON → `hitRateLimit` → `getHistory` → `answer()`
(до 15 с) → `appendHistory` → `sendMessage` → **и только потом** `200`.

Поток «кнопка»: `answerCallbackQuery` (спиннер гасится сразу) → `answer()` →
`editMessageText` → `200`.

Бюджет худшего случая: 15 с LLM + до 15 с Redis (два запроса по 5 с) + 10 с
`sendMessage` ≈ 40 с. Платформенный потолок Hobby — 300 с, Telegram ждёт ответ
порядка 60 с (эмпирика; в документации зафиксировано только «не-2xx → повтор»).

Вывод: схема валидна, но хвост близковат к таймауту Telegram, а идемпотентности
нет — повтор доставки обработается как новый вопрос.

## 2. Ack-after — решение и терминология

### Что означает «ack» (частая путаница)

**ack — это HTTP-ответ `200` на входящий POST от Telegram.** Это не сообщение
пользователю и не «сначала ответим текстом, потом поработаем». Текст ответа
отправляется **один раз**, одним вызовом `sendMessage`; `200` — служебное
подтверждение доставки, которое Telegram ждёт от нас.

Две разные оси, которые легко перепутать:

| Ось                     | Варианты                     | Что означает            |
| ----------------------- | ---------------------------- | ----------------------- |
| Когда отвечаем Telegram | ack-after / ack-first        | когда отдаём HTTP `200` |
| Когда пишем историю     | до отправки / после отправки | §5, независимая ось     |

«Ответили пользователю → записали историю» — это §5. К ack это отношения не
имеет: `200` можно отдать и до, и после `sendMessage`.

### Временная диаграмма (принятая схема)

```
Telegram ──POST /api/telegram──▶ функция
                                 ├─ GET  Redis  (история)      ~5–50 мс
                                 ├─ POST LLM                   2–15 с
                                 ├─ POST sendMessage           ~100–300 мс
                                 ├─ SET  Redis  (история)      ~5–50 мс
                                 └─ 200 ─────────────────────▶ Telegram
```

Один входящий запрос, ноль-два исходящих вызова Bot API, один `200` в конце.
Никакого «пользователь → функция → пользователь → функция»: второго входящего
запроса от Telegram нет, пока мы не ответили.

### Почему так

- Telegram требует только 2xx; повтор при не-2xx — это бесплатный retry,
  а не ошибка.
- Ack-first в serverless без внешней очереди **не гарантирует** выполнение:
  инстанс может быть заморожен сразу после ответа. `waitUntil` продлевает
  инвокацию, но живёт в пределах `maxDuration` и при таймауте **отменяет**
  промисы: обмен «повтор от Telegram» на «работа может потеряться молча».
- Настоящий ack-first требует очереди (QStash / Vercel Queues): +сервис,
  +секрет, +точка отказа. Для справочного бота — оверкилл.

## 3. `sendChatAction("typing")` — приоритет 1

**Проблема.** До 15 секунд пользователь видит тишину: LLM отвечает не мгновенно.

**Решение.** В `bot/telegram-api.ts` добавить `sendChatAction(chatId, action)`
(один `tgCall`, ничего нового), вызывать перед `answer()` в
`answerAsQuestion`. Ошибку глотать: индикатор — косметика, не повод терять ответ.

**Это не второе сообщение и не второй диалог.** `sendChatAction` — служебный
метод Bot API: он включает статус «печатает…» в шапке чата, **не создаёт
сообщение** в переписке, не попадает в историю и не требует ответа от
пользователя. Исходящих вызовов становится два, входящих — по-прежнему один:

```
Telegram ──update──▶ функция
                      ├─ sendChatAction("typing") ──▶ Telegram   (статус, не сообщение)
                      ├─ POST LLM                                  (2–15 с)
                      └─ sendMessage(ответ) ─────────▶ Telegram   (единственное сообщение)
```

Если бы мы отправляли текстом «Печатаю…», это действительно был бы «двойной
диалог» из двух сообщений. Мы этого не делаем: статус исчезает сам.

**Нюанс.** Telegram автоматически снимает «печатает» примерно через 5 с. Если
ответ дольше — либо не повторять (обычно LLM укладывается в 2–5 с), либо
повторять раз в ~4 с. Решение: **один вызов, без таймера** — не тратим время
функции и не плодим команды.

**Где:** `bot/telegram-api.ts`, `bot/http/telegram-webhook.ts`.
**Размер:** S. **Тесты:** мок `fetch` фиксирует вызов `sendChatAction` до
`chat/completions`.

## 4. Идемпотентность по `update_id` — приоритет 2

**Проблема.** Telegram — at-least-once: не-2xx или потерянный ответ → повтор
того же `update`. Сейчас повтор = второй вызов LLM, второе сообщение в чат,
вторая пара в истории.

**Решение — маркер ПОСЛЕ успешной обработки, проверка ДО.**

```
GET  tg:seen:{update_id}   → есть? значит уже обработали, вернуть 200 и выйти
…обработка (история → LLM → sendMessage)…
SET  tg:seen:{update_id} 1 EX 3600   → только после успешной отправки
```

Почему именно так:

- **маркер до работы** (SET NX в начале) ломает сценарий «функция убита по
  таймауту»: повтор увидит маркер и молча ничего не ответит. Это хуже дубля.
- **маркер после работы** корректен: Telegram не присылает один и тот же update
  двумя параллельными доставками — повтор возможен только после неудачи, то
  есть до установки маркера.
- сценарий «ответ потерялся в пути, но обработка прошла» закрывается именно
  этим: маркер уже стоит → повтор гасится.

**Детали.**

- `TgUpdate` получает поле `update_id: number`.
- Новые примитивы в `bot/store.ts`: `isSeen(key)` через `GET` и
  `markSeen(key, ttl)` через `SET key 1 EX ttl NX`. Вариант «SET NX в начале +
  `DEL` при исключении» — **не рекомендуется** (см. выше про kill).
- **Порядок проверок:** сначала dedupe, потом `hitRateLimit`. Иначе повтор
  съедает хит лимита и пользователь получает «слишком много вопросов» из-за
  доставки одного сообщения.
- **Fail-open:** Redis недоступен → `isSeen` возвращает «не видели» →
  обрабатываем как сейчас. Дедупликация — улучшение, а не условие работы.
- **Цена:** 2 команды Redis на апдейт (было 2–4), free-tier 500K/мес — не
  проблема.
- Покрывает и `message`, и `callback_query` (там та же проблема повтора).

**Где:** `bot/http/telegram-webhook.ts`, `bot/store.ts`, `bot/tests/`.
**Размер:** S–M. **Тесты:** повтор после успеха гасится; повтор после ошибки
доходит до LLM; без Redis — работает.

## 5. Порядок «отправить → записать в историю»

### 5.1. Telegram — делаем

**Проблема.** Сейчас сначала `appendHistory`, потом `sendMessage`. Если отправка
упала, в истории осталась пара, которой пользователь не видел. При повторе LLM
получает этот «фантомный» ответ в контексте и может продолжить старую мысль
вместо ответа на вопрос.

**Решение.** Поменять порядок: `sendMessage` → `appendHistory`.

Цена: если упадёт запись в историю после успешной отправки — пара не сохранится
(следующий вопрос пойдёт без этого контекста). Это деградация в пределах
fail-open и она менее заметна, чем фантомный ответ в контексте.

**Где:** `bot/http/telegram-webhook.ts` (`answerAsQuestion`).
**Размер:** S. **Тесты:** существующие тесты порядка `set`/`sendMessage`
обновить; добавить тест «sendMessage упал → в историю ничего не записалось».

### 5.2. Вебчат — порядок не меняется (ограничение платформы)

В вебчате «отправка» — это `return Response.json(...)`. Записать историю
**после** возврата ответа без `waitUntil` нельзя: функция завершится, и промис
может быть отброшен (та же причина, по которой отклонён ack-first, §2).

| Вариант    | Что делаем                                                                                           | Оценка                                                                          |
| ---------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| A (выбран) | оставить `append` перед `return`, зафиксировать асимметрию комментарием в коде и в `architecture.md` | 0 строк, честно                                                                 |
| B          | `waitUntil(appendHistory(...))` и `return` сразу                                                     | +зависимость `@vercel/functions` ради косметики; при таймауте запись отменяется |

У вебчата нет автоматического повтора (клиент сам решает, переспрашивать ли),
поэтому «фантомная пара» там гораздо менее вредна, чем в Telegram. Асимметрия
поведения каналов документируется как осознанная.

**Размер:** S (комментарий + docs).

## 6. Прочее по Telegram (по убыванию пользы)

### 6.1. `429 retry_after` в `tgCall` — S, опционально

Сейчас ошибка Telegram (`ok:false`) превращается в `Error`, и вызывающий код
пытается отправить fallback — который может упереться в тот же лимит.

Минимальный вариант: расширить тип ответа `parameters?: { retry_after?: number }`
и **логировать** его в тексте ошибки, без ожидания (сон внутри функции —
сожжённое время инвокации). Ждать имеет смысл только при разбиении длинного
ответа на части; но это уже полировка.

### 6.2. `answerCallbackQuery` в catch — оставить

Сейчас при ошибке повторно вызывается `answerCallbackQuery`. Это правильно:
спиннер не должен крутиться. Повторная ошибка глотается — тоже правильно.
Менять нечего, стоит зафиксировать как осознанное поведение в комментарии.

### 6.3. Секрет: сравнение без утечки времени — опционально

`request.headers.get(...) !== secret` — обычное сравнение строк. Для
256-битного секрета практического риска нет; если хочется строгости —
`crypto.timingSafeEqual` с предварительной проверкой длины. Ценность низкая.

### 6.4. `message.text.startsWith("/")` — опционально

`"/"` и `"/ "` попадают в `handleCommand` и получают «не знаю такую команду» —
приемлемо. Можно ужесточить до `/^\/[a-z]/i`, но выигрыш нулевой.

### 6.5. Ack-first — рассмотрено и отклонено

Условия, при которых к нему можно вернуться (если появились жалобы на дубли
или таймауты):

1. `waitUntil` из `@vercel/functions` — держит инвокацию до завершения промиса.
2. Собственная обработка ошибок остаётся (сейчас уже есть fallback-сообщение).
3. Осознанный отказ от повторов Telegram: упавшая в фоне работа не будет
   повторена платформой.
4. `maxDuration` заведомо больше бюджета (на Hobby дефолт 300 с — ок).
5. Дедупликация по `update_id` (§4) всё равно нужна как страховка от гонок.

Скелет для будущего варианта:

```ts
waitUntil(processUpdate(update));
return Response.json({ ok: true });
```

Плюс: нет дублей от повторов, пользователь не ждёт.
Минус: +зависимость, +класс ошибок «потеряли молча», +сложность отладки.

# Часть II. Архитектура `bot/`

## 8. Почему **не** объектная модель

Решение: не переписываем на классы. Кратко, чтобы не возвращаться:

| Что даёт ООП                        | Есть ли мотив здесь                                                        |
| ----------------------------------- | -------------------------------------------------------------------------- |
| Состояние/конфиг в инстансе         | Нет: Upstash REST без соединений, LLM/Telegram — HTTP, env = конфиг деплоя |
| Полиморфизм/подмена                 | Нет: один Redis, один LLM, два канала уже сведены к функциям               |
| Жизненный цикл (connect/close, пул) | Нет: `fetch` не требует жизненного цикла                                   |
| Много экземпляров (tenancy)         | Нет: один сайт, один бот                                                   |

Плюс: ESM-модуль — уже синглтон-объект с методами. Класс добавит `this`,
порядок инициализации и бойлерплейт, но не новые возможности.

**Настоящая проблема — неявные зависимости:** глобальные `fetch`,
`process.env`, `console`, состояние на уровне модуля (`lastSeenAt`,
`cachedEntries`, `cached`). Это лечится передачей зависимостей, а не классами.

**Когда вернуться к ООП:** появился второй провайдер/канал; переезд на
долгоживущий сервер (пул, graceful shutdown); мультитенантность. До этого —
не трогаем.

## 9. Принципы правок

- **Functional core / imperative shell:** чистые функции остаются функциями
  (`parseHistory`, `splitForLimit`, `startKeyboard`, `dumbAnswer`, `tokenize`).
- **Явные зависимости:** `fetch`, `env`, `log`, `now` передаются в фабрику.
- **Ленивый дефолт:** фабрика без аргументов работает как сейчас, чтобы не
  переписывать все вызовы сразу.
- Каждый шаг — отдельный коммит, зелёные `format:check lint typecheck test`.

## 10. Фаза A. Логгер с инстансным состоянием — S

**Проблема.** `lastSeenAt` живёт на модуле: тесты вынуждены брать уникальные
`module`/`key`, чтобы не влиять друг на друга; `Date.now()` не инжектируется
(нужны fake timers).

**Решение.**

```ts
export interface LoggerDeps {
  env?: NodeJS.ProcessEnv;
  now?: () => number;
  out?: Pick<Console, "debug" | "info" | "warn" | "error">;
}

export function createLogger(deps: LoggerDeps = {}) {
  /* Map внутри */
}

export const log = createLogger(); // обратная совместимость импорта
```

**Что меняется:** `bot/log.ts`, `bot/tests/log.test.ts` (без fake timers и без
уникальных ключей; добавить тест «два инстанса не гасят друг друга»).
**Совместимость:** `import { log }` во всех модулях не меняется.
**Риск:** низкий.

## 11. Фаза B. Транспорт Redis отдельно от домена — M

**Проблема.** `store.ts` (305 строк) смешивает три вещи: протокол Upstash,
политику домена (TTL, капы, парсинг) и ключи. Тесты подменяют глобальный
`fetch` через `vi.stubGlobal`.

**Шаг B1. `bot/redis-rest.ts`** — перенос `restEnv`, `runCommand`,
`runPipeline` без изменения поведения:

```ts
export interface RedisRestDeps {
  env?: NodeJS.ProcessEnv;
  fetchImpl?: typeof fetch; // ← важно: не захватывать globalThis.fetch при импорте
  log?: Logger;
  timeoutMs?: number;
}

export function createRedisRest(deps: RedisRestDeps = {}) {
  return { command, pipeline };
}
```

**Ловушка, которую надо явно учесть:** если фабрика захватит `globalThis.fetch`
на момент импорта, текущие тесты с `vi.stubGlobal` перестанут видеть подмену.
Дефолт должен резолвиться **внутри вызова** (`deps.fetchImpl ?? fetch`).

**Шаг B2.** `store.ts` остаётся доменом: `getHistory` / `appendHistory` /
`clearHistory` / `webKey` / `tgKey` / `ping` / `isSeen` / `markSeen` + капы и
`parseHistory`. Транспорт берёт из модульного `const redis = createRedisRest()`.

**Шаг B3.** Новые тесты `bot/tests/redis-rest.test.ts` переносят проверки
env-семейств, `{error}` при 200, non-2xx, таймаута и pipeline — уже без
глобального `fetch` (через `fetchImpl`). `store.test.ts` переводится на фейковый
`command`/`pipeline`, `vi.stubGlobal` из него уходит.

**Эффект:** store сокращается примерно до 180–200 строк и читается как «как
устроена история», а не «как устроен Upstash REST».

**Риск:** средний — это самый «горячий» код. Обязательное условие: поведение
1-в-1, все текущие тесты должны пройти без изменения ожиданий (кроме способа
подмены).

## 12. Фаза C. LLM-транспорт отдельно от «мозга» — M

**Проблема.** `brain.ts` (250 строк) содержит `fetch` к LLM, health-ping,
сборку промта (через `prompt.ts`), dumb-поиск и оркестрацию. `answer()` нельзя
протестировать без подмены глобального `fetch`; `pingLlm()` дублирует
timeout/parse-логику.

**Решение.**

- `bot/llm.ts` — `createLlm({ env, fetchImpl, clock })` → `chat(messages)`
  (бросает при любой проблеме, как сейчас `askLlm`) и `ping()` (никогда не
  бросает, как сейчас `pingLlm`).
- `brain.ts` остаётся: `HISTORY_WINDOW`, `FALLBACK_ANSWER`, `tokenize`,
  `dumbAnswer`, `answer()`.
- Дублирование «fetch + timeout + JSON» между `redis-rest`, `llm` и
  `telegram-api` **не выносим в общий хелпер**: у трёх мест разная семантика
  ошибок (fail-open / throw / ok:false). Общая функция сделает хуже.

**Тесты:** `brain.test.ts` получает `answer` с фейковым `llm.chat` (без сети и
без глобального fetch), `llm.test.ts` — транспорт.

**Риск:** низкий-средний.

## 13. Фаза D. Composition root и контракты — M

### D1. Порты (контракты) — `bot/contracts.ts`

Интерфейсы описывают **что** нужно обработчикам, без привязки к транспорту.
Реализации — адаптеры.

| Порт             | Методы (эскиз)                                                                                            | Адаптер                                        |
| ---------------- | --------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| `Clock`          | `now(): number`                                                                                           | системный (`Date.now`), в тестах — управляемый |
| `Logger`         | `debug/info/warn/error`, `warnThrottled`                                                                  | `createLogger()` (§10)                         |
| `RedisTransport` | `command(cmd)`, `pipeline(cmds)`                                                                          | `createRedisRest()` (§11)                      |
| `HistoryStore`   | `get`, `append`, `clear`, `isSeen`, `markSeen`                                                            | `createStore({ redis, log })`                  |
| `Llm`            | `chat(messages)`, `ping()`                                                                                | `createLlm({ env, fetchImpl, clock })` (§12)   |
| `Brain`          | `answer(question, history)`                                                                               | `createBrain({ llm, knowledge, log })`         |
| `TelegramApi`    | `sendMessage`, `sendChatAction`, `answerCallbackQuery`, `editMessageText`, `setWebhook`, `getWebhookInfo` | `createTelegramApi({ env, fetchImpl, clock })` |

Правила:

- порт живёт там, где его **потребляют** (история — в store, LLM — в brain);
  если файлов станет больше двух, `contracts.ts` разбивается по модулям;
- **никаких «на всякий случай» методов**: только то, что реально вызывается;
- зависимости идут в одну сторону: `contracts → adapters → app → api`.

### D2. Composition root — `bot/app.ts`

Собирает граф один раз и отдаёт готовые обработчики:

```ts
export function createApp(overrides: Partial<AppDeps> = {}) {
  const clock = overrides.clock ?? { now: Date.now };
  const log = overrides.log ?? createLogger({ now: clock.now });
  const redis = overrides.redis ?? createRedisRest({ log, env: process.env });
  const store = overrides.store ?? createStore({ redis, log });
  const llm = overrides.llm ?? createLlm({ log, clock, env: process.env });
  const brain = overrides.brain ?? createBrain({ llm, log });
  const tg = overrides.telegram ?? createTelegramApi({ clock, env: process.env });

  return {
    webchat: createWebChatHandler({ store, brain, log }),
    telegram: createTelegramWebhookHandler({ store, brain, tg, log }),
    admin: createTelegramAdminHandler({ store, llm, tg, log }),
  };
}

export const app = createApp(); // дефолт для `api/bot.ts`
```

`overrides` — единственный механизм подмены в тестах: ни `vi.stubGlobal`, ни
`vi.stubEnv` для новых тестов не нужны.

### D3. `api/bot.ts`

Остаётся роутером на ~30 строк: `switch (pathname)` → `app.webchat(request)` и
т. д. Никакой логики, никаких импортов адаптеров напрямую.

### D4. Что это даёт

- Читаемость: видно, из чего состоит приложение, в одном файле.
- Тесты: `api-router.test.ts` собирает `createApp({...фейки})` и проверяет
  маршрутизацию; обработчики тестируются без глобальных подмен.
- Замена реализации (например, in-memory store для локальной разработки) —
  одна строка в `createApp`, без правок обработчиков.

**Риск:** средний — самый большой диф. Митигация: D идёт последней, после A–C,
и не меняет поведение; каждый обработчик переводится на порт отдельным коммитом.

## 15. Критерии приёмки

1. `npm run format:check && npm run lint && npm run typecheck && npm run test` —
   зелёные на каждом шаге.
2. Ни одного `vi.stubGlobal("fetch")` в тестах _новых_ модулей (для `store`
   допускается до Фазы B включительно).
3. Публичное поведение не изменилось: коды ответов, fail-open, TTL, капы,
   набор throttle-ключей.
4. Суммарный `wc -l` по `bot/` вырос не более чем на ~15–20 % (выигрыш — в
   явных швах и контрактах, а не в объёме).
5. Обработчики не импортируют адаптеры напрямую: единственная точка сборки —
   `createApp` в `bot/app.ts`.
6. Ручная проверка на preview: `/start`, кнопка, обычный вопрос, `/reset`,
   повторная доставка (эмулировать двойным POST того же `update` из
   `?section=health`-диагностики или локально curl'ом).

## 16. Риски и откат

| Риск                                | Митигация                                                          |
| ----------------------------------- | ------------------------------------------------------------------ |
| Регрессия в fail-open store         | менять поведение только тестами; фаза B — отдельный коммит         |
| Захват `globalThis.fetch` в фабрике | дефолт резолвится внутри вызова; тест на подмену после импорта     |
| Дедупе гасит легитимный повтор      | маркер ставится **после** успешной отправки; TTL 1 ч               |
| Новый шум в логах                   | throttle-ключи сохраняются как есть                                |
| Разрастание диффа                   | каждая фаза — отдельный PR; D идёт последней и не меняет поведение |

Откат любой фазы — revert одного коммита: фазы не переплетены, кроме D
(последняя).

## 17. Вне рамок этой задачи (зафиксировано, чтобы не потерять)

- `rate-limit` использует `key = rate:${bucket}` с IP/chatId → у `warnThrottled`
  неограниченная кардинальность ключей в долгоживущем инстансе. Возможное
  лечение: константный ключ `"exceeded"` (точный бакет и так в тексте).
- Переход на `@upstash/redis` SDK — отклонён: выигрыш косметический, а
  семантика ретраев/десериализации/телеметрии требует ручной настройки, чтобы
  не ухудшить fail-open.
- Логирование `update_id` — можно добавить вместе с §4 для трассировки.
