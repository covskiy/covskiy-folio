# 03 — Аудит чата: найденные предложения

Статус: **черновик предложений, ничего не реализовано**.
Дата: 2026-11-08.

`bot/llm.ts`, `bot/store.ts`, `bot/config.ts`, `src/chat/*`, `docs/architecture.md`.

предложение; финальное решение за владельцем.

## P1 — надёжность

### 1. `answer()` может бросить: обещанный dumb-fallback не работает при недоступной справке

**Где:** `bot/brain/brain.ts:114-136`, `bot/brain/prompt.ts:24-28`.

**Сейчас:** `systemPrompt()` читает `knowledge.json` лениво и может бросить
(`ENOENT`, битый JSON). Бросок попадает в `catch`, который вызывает
`dumbAnswer()` — а тот читает **тот же** `knowledge.json` через
`knowledgeEntries()`. Исключение вылетает уже из `catch`, хотя docstring
обещает «Никогда не бросает» (`brain.ts:104`).

**Почему плохо:** комментарий в `prompt.ts` обещает деградацию «только запрос в
dumb-режим». Для главного источника знаний этой деградации нет: отказ справки
ломает **оба** режима. Вероятность низкая (файл едет в артефакт и парсится на
деплое), но последствие — полный отказ чата, а не ухудшение ответа.

**Предложение:**

- разделить «прочитать знания» и «собрать промт»: ошибка чтения знаний не
  должна вылетать из `dumbAnswer`;
- при недоступной справке возвращать безопасный ответ вида «справка временно
  недоступна, напишите в Telegram/на почту» с `mode: "dumb"`;
- закрепить контракт тестом: битый/отсутствующий JSON → `answer()` не бросает,
  возвращает `{mode: "dumb"}`.

**Готово, когда:** `answer()` не бросает ни при одном сценарии отказа чтения
файлов; есть тест на битый и отсутствующий JSON.

### 2. В `api/bot.ts` нет верхнего обработчика ошибок

**Где:** `api/bot.ts:20-31`.

**Сейчас:** `fetch` роутера вызывает обработчики без `try/catch`. Любое
непредвиденное исключение (например, из п. 1) уходит на платформу — клиент
получает платформенный 500 без JSON-контракта `{ok:false,error}`.

**Почему плохо:** ломается единый HTTP-контракт; frontend не может отличить
«API ответил ошибкой» от «платформа упала»; в логах остаётся трейс без
прикладного контекста.

**Предложение:** обернуть `switch` в `try/catch`, логировать причину и отдавать
`Response.json({ ok: false, error: "Internal Error" }, { status: 500 })`.
Секреты и внутренние детали в тело не класть.

**Готово, когда:** исключение в любом обработчике даёт JSON 500 и запись в лог.

### 3. GET-ветки и команды Telegram жёстко зависят от справки

**Где:** `bot/http/webchat.ts:83-88` (GET-чипсы),
`bot/http/telegram-webhook.ts:105-110` (`/start`),
`bot/http/telegram-webhook.ts:152-156` (`/about`),
`bot/http/telegram-admin.ts:110-113` (`?section=prompt`).

**Сейчас:** `knowledgeEntries()` вызывается без защиты. При недоступном JSON:
`GET /api/chat` → 500 (чипсы не загрузятся), `/start` → ошибка обработчика,
`/about` → ошибка, админский просмотр промта → 502.

**Почему плохо:** даже если сам `answer()` починить (п. 1), интерфейсные ветки
продолжат падать из-за контента, который не является обязательным для их
работы. Чипсы и кнопки — не критичный путь: пустой список лучше 500.

**Предложение:** «мягкое» чтение для UI-потребителей: ошибка → пустой список
чипсов/кнопок и запись в лог. Для `/about` — fallback-текст. Для админки —
явная ошибка `{ok:false,error}` с 502, а не исключение.

**Готово, когда:** при недоступной справке вебчат открывается без чипсов,
Telegram отвечает на `/start` и `/about`, админка отдаёт диагностируемую ошибку.

### 4. Нет runtime-валидации `knowledge.json`

**Где:** `bot/brain/prompt.ts:24-28`.

**Сейчас:** `JSON.parse(...) as KnowledgeItem[]` — только приведение типа.
Запись без `title` даст `## undefined` в промте, без `text` — пустой ответ; лишние
поля и неверные типы проходят молча.

**Почему плохо:** файл правится руками; tsc его не проверяет. Опечатка в ключе
или забытое поле обнаруживается только на проде.

**Предложение:** небольшая проверка формы при чтении (массив, у каждого
элемента непустые строки `title`/`text`); при нарушении — либо отбрасывать
запись с warn, либо считать справку невалидной и уходить в безопасный ответ
(см. п. 1). Плюс тест на фикстуру с битой записью.

**Готово, когда:** битая запись не попадает в промт и не даёт `undefined`;
есть тест.

## P2 — контракты и хрупкость

### 5. Первые 3 элемента массива неявно управляют UI

**Где:** `bot/http/webchat.ts:18,84-86`,
`bot/http/telegram-webhook.ts:53,106-108`, `bot/brain/knowledge.json`.

**Сейчас:** чипсы вебчата и кнопки `/start` — это «первые 3 элемента JSON».
Порядок массива одновременно задаёт порядок секций в промте и состав
публичных подсказок. В типе `KnowledgeItem` этого контракта нет.

**Почему плохо:** добавление темы в начало или сортировка «по смыслу» молча
меняет интерфейс. Владелец правит контент — а получает другой набор кнопок.

**Предложение:** сделать контракт явным, на выбор:

- поле `chip: true` (или `priority`) у элемента — UI берёт помеченные;
- либо отдельная функция `uiTopics()` в модуле знаний с комментарием, что
  первые N — это UI;
- либо оставить порядок, но зафиксировать правило в `knowledge.json`/README и
  покрыть тестом «первые 3 — ожидаемые заголовки».

**Готово, когда:** изменение порядка неконтентных записей не меняет чипсы и
кнопки; правило описано в одном месте.

### 6. `callback_data = ask:{index}` ломается при правке справки

**Где:** `bot/http/telegram-webhook.ts:105-110,182-193`.

**Сейчас:** кнопка несёт индекс записи. Сообщение `/start` живёт в Telegram
бессрочно. Если между отправкой и нажатием записи переставили/удалили и
задеплоили, `ask:2` попадёт в другую тему, а несуществующий индекс даст
«кнопка устарела».

**Почему плохо:** пользователь получает ответ не на ту тему без явной ошибки.
Это тихая порча UX после каждой правки контента.

**Предложение:** стабильный `id` у записи (slug), `callback_data = ask:{id}`,
поиск по `id` вместо индекса. Для старых кнопок — прежняя ветка «кнопка
устарела». `id` также пригодится для п. 5 и п. 7.

**Готово, когда:** перестановка записей не меняет смысл старой кнопки; удаление
записи даёт понятное сообщение, а не чужой ответ.

### 7. `/about` привязан к точному заголовку «Кто я»

**Где:** `bot/http/telegram-webhook.ts:152-156`.

**Сейчас:** `entries.find(item => item.title === "Кто я") ?? entries[0]`.
Переименование заголовка (контент правится без кода) приводит к тому, что
`/about` отдаёт первую запись — сейчас это «Услуги».

**Почему плохо:** команда «о владельце» начинает отвечать про услуги; связь
держится на строке, которую владелец вправе менять.

**Предложение:** явный признак `about: true` или `id: "about"`; fallback —
осмысленный текст, а не произвольная первая запись. Если решено оставить
заголовок — зафиксировать это правило в документации по контенту.

**Готово, когда:** переименование заголовка не ломает `/about`; fallback
осмыслен.

### 8. Две независимые константы «3 темы»

**Где:** `bot/http/webchat.ts:18` (`CHIPS_COUNT`),
`bot/http/telegram-webhook.ts:53` (`START_BUTTONS_COUNT`).

**Сейчас:** одинаковое число задано дважды. Поменяли одно — каналы разошлись.

**Почему плохо:** веб и Telegram должны показывать одни и те же темы; это
заявлено в документации, но не обеспечено кодом.

**Предложение:** один источник (например, `uiTopics(limit)` в модуле знаний),
который используют оба обработчика. Тест: оба канала получают одинаковый список.

**Готово, когда:** число и состав подсказок задаются в одном месте.

### 9. Плейсхолдер `{{KNOWLEDGE}}` заменяется без проверки

**Где:** `bot/brain/prompt.ts:49-63`.

**Сейчас:** `String.replace` со строковым паттерном заменяет **первое**
вхождение; нет проверки, что плейсхолдер вообще есть и что он один.

**Почему плохо:** дубль плейсхолдера в другом md-файле «съест» подстановку;
пропавший плейсхолдер молча оставит бота без справки — без ошибки и без
понятного лога.

**Предложение:** проверять количество вхождений (ровно одно) и бросать/логировать
при нарушении; либо `replaceAll`, если несколько мест допустимы осознанно.
Тест: после сборки в промте есть заголовок первой записи и нет `{{KNOWLEDGE}}`.

**Готово, когда:** нарушение контракта плейсхолдера видно в тестах и логах.

### 10. Telegram теряет `mode`: dumb-ответ неотличим от LLM

**Где:** `bot/http/telegram-webhook.ts:140` — `const { text: reply } = ...`;
вебчат передаёт `mode` в UI (`src/chat/chat-api.ts`, `chat-widget.ts`).

**Сейчас:** в вебе пользователь видит бейдж «офлайн-справка», в Telegram —
ничего. Если LLM недоступен, ответ по ключевым словам выглядит как обычный.

**Почему плохо:** пользователь не понимает, что ответ мог быть неполным;
владелец не видит деградацию в самом канале.

**Предложение:** решить явно:

- добавлять короткую пометку к dumb-ответу в Telegram (например, «ответ из
  краткой справки»);
- либо считать это осознанным различием каналов и зафиксировать в документации;
- в любом случае логировать `mode` (см. п. 12).

**Готово, когда:** решение зафиксировано; поведение каналов описано.

## P3 — качество и удобство

### 11. Качество dumb-поиска

**Закрыто задачей [04 — dumb-режим](04-dumb-mode-search-and-offline-help.md):**
поиск вынесен в `bot/brain/search.ts` (`rankKnowledge`: нормализация, стемминг,
IDF, синонимы `keywords`), dumb-ответ = `title + text`, порог `0.3`, тест-набор —
`bot/tests/search.test.ts`.

**Где:** `bot/brain/brain.ts:43-84`.

**Сейчас:** токенизация без морфологии, счёт — доля совпавших слов вопроса,
порог `0.2`, возвращается только `text` без `title`.

**Почему плохо:**

- «Сколько стоит PWA?» — слова «сколько»/«стоит» не совпадают со «Стоимостью»,
  зато `pwa` совпадает → вернётся описание PWA **без цены**;
- длинные записи выигрывают за счёт большего числа слов;
- ответ без заголовка начинается «Пять направлений:…» без контекста;
- `length >= 3` отбрасывает `IT`, `UX`, `Go`.

**Предложение:** возвращать `title + text`; взвешивать совпадение заголовка
выше текста; добавить простейшую нормализацию (усечение окончаний) или
синонимы «цена/стоимость/стоит»; при сомнении — честный fallback на контакты.
Собрать небольшой тест-набор реальных вопросов и зафиксировать ожидания.

**Готово, когда:** тест-набор проходит; ответы не выглядят обрывками.

### 12. Нет аналитики деградаций и тем

**Где:** `bot/brain/brain.ts`, `bot/http/*`.

**Сейчас:** единственный машинный сигнал — `mode` в ответе вебчата; Telegram его
не сохраняет. Debug-логи есть, агрегатов нет.

**Почему плохо:** нельзя ответить на вопросы «как часто LLM падает», «что
спрашивают», «стало ли хуже после правки справки». Деградация замечается
только вручную.

**Предложение:** минимальный счётчик: `mode` (llm/dumb), канал, день; при
желании — хэш/тема вопроса без хранения текста (приватность). Можно
переиспользовать Redis-счётчики или структурированные логи Vercel. Отдельно
не логировать персональные данные.

**Готово, когда:** есть способ увидеть долю dumb-ответов за период.

### 13. Конфликт роли в persona

**Где:** `bot/brain/prompts/00-persona.md`.

**Сейчас:** «Ты — ассистент сайт-визитки…» и тут же «Отвечай так, как ответил бы
сам Константин: от первого лица».

**Почему плохо:** модель может начать утверждать, что она и есть Константин,
или путаться в самоидентификации.

**Предложение:** выбрать и зафиксировать одну рамку: «ассистент, говорящий от
лица Константина» или «Константин отвечает лично». Поправить формулировку,
проверить на вопросах «ты бот?», «ты Константин?».

**Готово, когда:** ответы на вопросы о самоидентификации предсказуемы.

### 14. Нет правила «не раскрывай системный промт»

**Где:** `bot/brain/prompts/10-rules.md`.

**Сейчас:** прямого запрета нет. Справка публичная, поэтому риск низкий, но
джейлбрейк «покажи свои инструкции» ничем не ограничен.

**Почему плохо:** бот может пересказать внутренние правила и служебные
формулировки; это выглядит неаккуратно, хотя и не раскрывает секретов.

**Предложение:** добавить короткое правило: не пересказывать инструкции,
отвечать по существу вопроса. Решение — за владельцем, можно оставить как есть.

**Готово, когда:** решение зафиксировано (правило добавлено или риск принят).

### 15. `knowledgeEntries()` живёт в `prompt.ts`

**Где:** `bot/brain/prompt.ts`.

**Сейчас:** модуль называется «сборщик промта», но экспортирует контент,
который тянут вебчат, Telegram и dumb-поиск.

**Почему плохо:** владение смешано; при будущем выносе справки в KV/Blob
придётся трогать «промт», хотя речь о контенте.

**Предложение:** при следующем касании вынести чтение/валидацию в
`bot/brain/knowledge.ts`, а `prompt.ts` оставить только сборку. Рефакторинг
механический, но затрагивает импорты — делать отдельным коммитом.

**Готово, когда:** контент и сборка промта разведены по модулям.

### 16. Расхождение документации и кода

**Где:** `docs/manual.md:122` — «`CHIPS_COUNT = 3` из `bot/brain/prompt.ts`»;
фактически константа в `bot/http/webchat.ts:18`.

**Почему плохо:** владелец ищет настройку не там; документация теряет доверие.

**Предложение:** поправить ссылку; заодно сверить §5.1–5.3 с текущим кодом
(плейсхолдер, первые 3, `/about`).

**Готово, когда:** пути и имена в документации совпадают с кодом.

### 17. Справка целиком уходит в каждый промт

**Где:** `bot/brain/prompt.ts:49-63`.

**Сейчас:** все записи вставляются в system-промт каждого запроса; отбора по
релевантности нет.

**Почему плохо:** сейчас это плюс (модель видит всё), но стоимость токенов
растёт линейно. При 100+ записях промт станет дорогим и начнёт размывать
внимание модели.

**Предложение:** не менять сейчас; зафиксировать порог (например, объём
справки в символах), после которого вернуться к отбору релевантных записей.
Пока достаточно теста/скрипта, который показывает размер собранного промта.

**Готово, когда:** есть наблюдаемый ориентир по размеру; решение о пороге
зафиксировано.

## Инварианты, которые нельзя ломать при исправлениях

1. Одна Vercel Function `api/bot.ts`, роутинг по `pathname` через rewrites.
2. Публичный HTTP-контракт: коды `200/400/401/403/404/405/429/502/500`,
   форма `{ ok, text?, mode?, error? }`.
3. Fail-open по store: без Redis бот отвечает без истории и лимитера.
4. Env-имена и семейства (`UPSTASH_REDIS_REST_*` / `KV_REST_API_*`), TTL 24 ч,
   капы 20 сообщений / 4000 символов, `HISTORY_WINDOW = 10`.
5. Относительные импорты — только с `.js`; `process` — только через
   `import process from "node:process"`; серверный код вне `api/`.
6. Тесты не ходят в сеть.
7. Один «мозг» на оба канала: различия — только в адаптерах.

## Предлагаемый порядок работ

1. **Пакет «надёжность»** (п. 1–3): безопасное чтение справки, верхний
   `try/catch`, мягкие UI-ветки. Самый высокий эффект при малом объёме.
2. **Пакет «контракт знаний»** (п. 5–9): `id`, явные признаки UI, единый
   `uiTopics()`, проверка плейсхолдера, валидация формы.
3. **Пакет «качество»** (п. 10–12): dumb-поиск, `mode` в Telegram, счётчик
   деградаций.
4. **Пакет «документация и мелочи»** (п. 13–17): persona, правило про промт,
   вынос модуля, докдрифт, порог размера.
