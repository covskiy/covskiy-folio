# Архитектура

> Как всем этим пользоваться и чинить — мануал владельца в [manual.md](manual.md).

## Общая схема

```
Браузер (статика: Vite MPA, dist/)                    Telegram
   │  POST /api/chat {sessionId, text}                   │  POST /api/telegram (update)
   ▼                                                     ▼
        ┌──────────────── vercel.json (rewrites) ────────────────┐
        │            /api/chat  ─┐            /api/telegram ─┐   │
        └────────────────────────┼───────────────────────────┼───┘
                                 ▼                           ▼
                     ┌───────────────────────────────────────────┐
                     │        api/bot.ts — ОДНА функция          │
                     │        роутер по pathname                 │
                     └──────────────┬────────────────────────────┘
                                    ▼
                     bot/http/webchat.ts        bot/http/telegram-webhook.ts
                             └──────┬──────┘
                     bot/store.ts — история диалога в Upstash Redis
                        (REST; недоступен → stateless, fail-open)
                                    ▼
                            bot/brain/brain.ts — answer()
                        LLM (OpenAI-совместимый API)
                                   ↘ при ошибке/таймауте
                        dumb-поиск: bot/brain/search.ts
                        по bot/brain/knowledge.json
```

Третий rewrite ведёт в ту же функцию админ-маршрут `/api/telegram-setup`
(диагностика, вебхук, просмотр промта) — описан ниже.

## Почему одна функция, а не две

Файлы в корневом `api/` Vercel деплоит как отдельные функции. Свежая рекомендация
документации Vercel: держать связанные маршруты в **одной общей функции** — тогда
Fluid compute переиспользует один инстанс для всех источников (меньше холодных
стартов), в дашборде один объект, и общий код `brain`/`store` грузится один раз.

Чтобы URL остались семантичными (`/api/chat`, `/api/telegram`, `/api/telegram-setup`),
в `vercel.json` настроены rewrites на `/api/bot`. Это единственный `vercel.json` в
проекте — Vite детектится и собирается сам (`vite build` → `dist/`).

Сигнатура функции — современный Web-стандарт (рекомендация Vercel):

```ts
export default {
  async fetch(request: Request): Promise<Response> { … }
};
```

## Контент и промт — bot/brain/knowledge.json + bot/brain/prompts/*.md

Справка («мозг» бота) живёт в данных, не в коде:

- `bot/brain/knowledge.json` — массив `{id, title, text, keywords?, contact?,
  chip?, about?}`, источник истины для справки. UI берёт одни и те же
  `uiTopics()` (помеченные `chip: true`, максимум 3) — чипсы вебчата, кнопки
  `/start` и подсказки fallback; `/about` — запись с пометкой `about: true`.
  `keywords` (синонимы для dumb-поиска) и `contact: true` (запись-контакт:
  гарантированная подсказка dumb-fallback, чтобы офлайн-режим всегда оставлял
  путь к владельцу) — поисковый слой: в промт и UI они не попадают. Порядок
  массива задаёт только порядок секций промта.
- `bot/brain/knowledge.ts` — хранилище справки: `load()` — безопасное чтение
  (валидация формы: битая запись отбрасывается с warn, мусорный `keywords`
  удаляется, `contact` не `true` игнорируется — fail-soft, запись живёт;
  непарсируемый JSON → null; никогда не бросает; исход кэшируется),
  `uiTopics()` — единый источник UI-тем, `ID_PATTERN` — формат slug'а `id`.
  Чтение — `readFileSync` с литеральным `new URL(...)` относительно модуля:
  только такие пути nodeFileTrace затрейсит в артефакт функции (таблица — в
  «Граблях платформы»).
- `bot/brain/search.ts` — dumb-поиск: `rankKnowledge(question, entries)`
  ранжирует записи — нормализация (lowercase, ё→е, стоп-слова вырезаются
  и из вопроса, и из записей; allowlist коротких IT/UX/UI/AI), лёгкий стемминг
  русских окончаний, IDF-вес слов (редкие весят больше частых), вес полей
  `title`/`keywords` 1.0 и `text` 0.5. Возвращает все ненулевые попадания по
  убыванию score — порог уверенности это политика brain.ts (`DUMB_SCORE_THRESHOLD
  = 0.3`: уверенное попадание → ответ `title + text`, промах → fallback с
  подсказками: до 2 near-miss → контакт `contact: true` → `uiTopics`, максимум
  3, дедуп по id). Модуль доменной логики: не бросает, не читает файлы, не
  ходит в сеть; индекс кэшируется по идентичности массива записей (WeakMap).
- `bot/brain/help.ts` — тексты помощи (`HELP_TEXT_WEBCHAT`, `HELP_TEXT_TELEGRAM`,
  `HELP_TEXT_WEBCHAT_FALLBACK`). Помощь — интерфейсная команда, а не знание:
  не живёт в `knowledge.json` и не зависит от LLM, Redis и доступности справки.
  Модуль без импортов — его импортирует и клиент вебчата, в бандл уходит только
  строка.
- `bot/brain/prompts/00-persona.md`, `10-rules.md`, `20-knowledge.md` — разделы system
  prompt готовым текстом, без парсинга; единственная обработка — `trim()` и
  строковая подстановка плейсхолдера `{{KNOWLEDGE}}` в 20-knowledge.
- `bot/brain/prompt.ts` — сборщик: `systemPrompt(entries)` склеивает md-разделы
  и вставляет переданную справку (записи приходят из knowledge.ts — сборщик
  сам JSON не читает). md-читается литеральными `new URL(...)`, сборка
  кэшируется по идентичности массива записей (WeakMap) — чтение с диска
  лямбды один раз, не на каждый запрос.

Контент вшивается в артефакт на деплое (как и env): правка справки или промта =
пуш → деплой → оба канала отвечают по-новому.

## Конфигурация и транспорты — bot/config.ts, bot/llm.ts, bot/redis-rest.ts

- `bot/config.ts` — единая точка чтения env: типизированные слайсы `llm`, `redis`,
  `telegram`, `rateLimit`, `logLevel`. Парсинг и дефолты (trim, срез хвостовых
  слэшей, `Number(...)` с дефолтом) живут здесь, потребители получают готовые
  значения — опечатка в имени переменной ловится tsc в месте потребления
  (декларации ProcessEnv в `bot/env.d.ts` это не ловили, остался только `PORT`
  для vite.config.ts). Геттеры ленивые: env перечитывается на каждый доступ,
  подмена после старта процесса остаётся видимой; при этом env, как и прежде,
  «запекается» в деплой (Redeploy после правки переменных).
- `bot/llm.ts` — транспорт LLM: единственное место с `fetch` в
  OpenAI-совместимый endpoint (Ollama Cloud, llama.cpp, …). Никакой доменной
  логики: system-промт собирает brain (`bot/brain/brain.ts`), транспорт получает
  готовый массив сообщений. `chat()` бросает при любой проблеме (brain падает в
  dumb-режим), `ping()` для health никогда не бросает.
- `bot/redis-rest.ts` — транспорт Upstash REST: команда — JSON-массив в теле
  POST, чистый `fetch` без SDK (REST-эндпоинт один, зависимости не нужны).
  Fail-open: любая проблема даёт `null` + warn, не throw. Вынесен из store.ts,
  чтобы домен читался как «как устроена история», а не «как устроен Upstash».
- `bot/log.ts` — фабрика `createLogger()` (состояние троттлинга — инстансное,
  в замыкании) с дефолтным `log`; уровень — `config.logLevel` (env `LOG_LEVEL`,
  дефолт warn), формат `[модуль] сообщение`.

## Память диалога — bot/store.ts

- Upstash Redis по REST API: протокол — транспорт `bot/redis-rest.ts` (см.
  «Конфигурация и транспорты» выше), `store.ts` — только домен: операции над
  ключами (TTL, капы, парсинг), дедупликация и лимитер.
- Ключи: `chat:web:{sessionId}` (вебчат) и `chat:tg:{chatId}` (Telegram). История —
  одно значение: JSON-массив `{role, content}`, читается и пишется целиком одним
  SET (атомарно; гонки concurrent-запросов одного чата для визитки не критичны —
  last-write-wins).
- TTL 24 часа (env `HISTORY_TTL_SECONDS`), обновляется при каждой записи —
  «скользящее окно» активности. В промт идут последние 10 сообщений
  (env `HISTORY_WINDOW`; оба — слайсы history/brain в `bot/config.ts`).
- **Fail-open.** Любая проблема — нет env, сеть, не-200, ошибка в ответе, битый
  JSON — даёт пустую историю и warn в лог (`[store]`), запрос не падает: бот
  обязан отвечать и без Redis, в stateless-режиме (контекст — только текущий
  вопрос).
- `/reset` (Telegram) удаляет ключ; «новый диалог» вебчата — новый sessionId
  (старый ключ истечёт по TTL сам).

## Вебчат — bot/http/webchat.ts + src/chat/

- Клиент шлёт только `{sessionId, text}`. sessionId генерирует
  `crypto.randomUUID()` и хранит в localStorage — контекст переживает
  перезагрузку страницы; сам транскрипт — в памяти виджета.
- Сервер: история из Redis → `answer(question, history)` → пара вопрос/ответ
  обратно в историю → `{ok, text, mode, suggestions?}`: подсказки следующего
  вопроса (`{title}`, без id) прилагает brain только к dumb-fallback — у
  llm-ответа, уверенного dumb-ответа и недоступной справки поля в JSON нет.
  Подсказки — UI-слой: в историю диалога не пишутся.
- `GET /api/chat` — `{ok, service, chips, help}`: `uiTopics()` из knowledge.ts
  (записи с пометкой `chip: true`, максимум 3) — те же темы, что кнопки /start
  (чипсы развёрнутого виджета); недоступная справка — пустой список, не 500.
  `help` — статический текст из brain/help.ts, отдаётся всегда: кнопка «?»
  обязана работать и в offline-режиме.
- Валидация: sessionId — белый список `[A-Za-z0-9_-]{8,64}` (он часть ключа
  Redis), text — непустая строка до 2000 символов.
- `src/chat/chat-api.ts` — клиент: `fetchChatBootstrap()` (чипсы + help, один
  GET за жизнь страницы, ошибка → пусто, не бросает) и `askChat()` (возвращает
  `suggestions?: ChatChip[]`, максимум 3).
- `src/chat/chat-widget.ts` — UI: плавающая кнопка, панель, индикатор
  «печатает…», бейдж «офлайн-справка» для `mode=dumb`, кнопка «?» (текст помощи
  из бутстрапа + чипсы, без POST) и локальные команды `/help`/`/start` — точное
  совпадение ввода, в POST и историю не идут. Подсказки dumb-fallback рисуются
  тем же рядом чипов, клик — обычный вопрос. Никакого innerHTML с данными
  пользователя — только `textContent`.

## Telegram — bot/http/telegram-webhook.ts + bot/telegram-api.ts

- Webhook принимает только POST с заголовком `X-Telegram-Bot-Api-Secret-Token`,
  равным `TELEGRAM_WEBHOOK_SECRET` (секрет задаётся при setWebhook). Иначе — 401:
  чужие запросы не тратят вызовы LLM.
- Дедупликация апдейтов по `update_id` (Telegram — at-least-once: при не-2xx или
  потерянном ответе он повторяет ТОТ ЖЕ JSON; повтор неотличим от нового
  вопроса — второй вызов LLM, вторая пара в истории). Порядок: GET маркера
  `tg:seen:{update_id}` **до** обработки (есть маркер — уже отвечали, `200 {ok:true}`
  и выход), SET маркера (`EX 3600 NX` — примитивы `isSeen`/`markSeen`/`tgSeenKey`
  в `bot/store.ts`) **после** успешной обработки. Маркер после, а не до: маркер
  до работы ломает сценарий «функция убита по таймауту» — повтор увидел бы
  маркер и молча не ответил, это хуже дубля. Дедупликация до лимитера: иначе
  повтор съедает хит лимита, и пользователь получает «слишком много вопросов»
  из-за доставки одного сообщения. Fail-open: без Redis (или при ошибке Redis)
  дедупликация просто отключается — бот отвечает как раньше.
- Свободный текст и нажатая inline-кнопка идут одним потоком: `sendChatAction`
  «печатает…» (ошибка глотается — косметика) → история из Redis → `answer()` →
  `sendMessage` → пара вопрос/ответ в историю. Порядок «отправить → записать»:
  при упавшей отправке в историю не должно попасть ничего — фантомная пара
  осталась бы в контексте, и при повторе LLM продолжал бы старую мысль. У
  вебчата порядок обратный — см. bot/http/webchat.ts. Команды (`/start`,
  `/help`, `/reset`, `/about`) в историю не пишутся — это действия интерфейса,
  а не реплики диалога.
- `/start` — приветствие + inline-кнопки (`uiTopics()` — те же темы, что чипсы
  вебчата). Кнопка несёт `callback_data = "ask:{id}"` — slug записи: правка
  контента не меняет смысл старой кнопки, а удаление/переименование `id` уводит
  её в ветку «кнопка устарела» (лимит Telegram 64 байта — slug влезает с запасом).
  `answerCallbackQuery` гасит спиннер сразу, не дожидаясь LLM; `editMessageText`
  снимает одноразовую клавиатуру со старого сообщения.
- `/help` — текст помощи из brain/help.ts + те же кнопки тем (`startKeyboard()`):
  помощь кликабельна и работает без LLM; недоступная справка → только текст.
- Подсказки dumb-fallback — та же inline-клавиатура `ask:{id}` при ответе бота:
  клик идёт в существующий `handleCallbackQuery`, как нажатие кнопки /start.
  Подсказки не пишутся в историю и не тратят лимит; контакт гарантирован
  записью с `contact: true` — офлайн-режим всегда оставляет путь к владельцу.
- `/about` — запись справки с пометкой `about: true`; заголовок записи владелец
  переименовывает свободно. Пометки нет или справка недоступна — осмысленная
  заглушка, а не произвольная первая запись.
- `sendMessage` режет ответы длиннее 4096 символов (лимит Telegram на одно
  сообщение) — по последнему переводу строки в окне.
- Ошибки отправки/LLM ловятся, наружу всегда отдаётся 200 (иначе Telegram будет
  повторять доставку update). Сообщения без текста (фото, стикеры) грациозно
  игнорируются.
- `bot/telegram-api.ts` — тонкая обёртка Bot API на `fetch`, без зависимостей:
  `sendMessage`, `editMessageText`, `answerCallbackQuery`, `sendChatAction`,
  `setWebhook`, `getWebhookInfo`. Токен и корень Bot API (`TELEGRAM_API_ROOT`,
  дефолт — официальный) — слайс `config.telegram` из `bot/config.ts`.

## Админ-маршрут — /api/telegram-setup (bot/http/telegram-admin.ts)

Один путь (третий rewrite), ветвление по query-параметру `section` — подпути
через `vercel.json` не заводим. Зачем: регистрация вебхука без прямого доступа к
api.telegram.org (у части провайдеров заблокирован), health бота и просмотр
собранного промта. Защищён тем же секрет-заголовком, что и вебхук; без секрета —
404 (маршрут скрыт).

| Запрос                | Ответ                                                                                                                                                                   |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET `?section=health` | `{llm, redis, telegram}` — `llm.ping()` (из `bot/llm.ts`) + `ping()` (из `bot/store.ts`) + `getWebhookInfo()`, параллельно; ошибка одного пункта не влияет на остальные |
| GET `?section=prompt` | собранный промт целиком (`systemPrompt(entries)`; секрет есть — справка не отдельная сущность); справка недоступна — 502 с причиной в теле                              |
| GET без section       | `getWebhookInfo` — историческое поведение                                                                                                                               |
| POST                  | `setWebhook`: `url` из origin запроса, `secret_token` из env, `allowed_updates: ["message", "callback_query"]`                                                          |
| прочие методы         | 405                                                                                                                                                                     |

## Безопасность

- Секреты живут только в env (Vercel) и `.env.local` (в `.gitignore`). На фронте
  секретов нет вообще — `/api/chat` публичный по дизайну (это справка).
- Webhook защищён secret-заголовком; без валидного секрета — 401. Админ-маршрут —
  тем же секретом, но без валидного секрета отвечает 404 (не подтверждает
  существование маршрута).
- Валидация входа: sessionId-паттерн (он часть ключа Redis), длина текста,
  роли сообщений — защита от мусорных запросов и произвольных ключей.
- CORS не настраивается: сайт и `/api` на одном домене (same-origin).
- Стены против злоупотреблений (цель — не дать штормом выжечь free-квоты
  Ollama/Upstash/Vercel, порядок — от дешёвой проверки к дорогой):

  | Стена                      | Что ловит                                                                                                               | Код                         |
  | -------------------------- | ----------------------------------------------------------------------------------------------------------------------- | --------------------------- |
  | same-origin на POST        | drive-by из чужих страниц: браузер ставит Origin сам, JS не подделает; curl без Origin пропускается — его ловит лимитер | `webchat.ts` (`sameOrigin`) |
  | rate-limit 15/час на ключ  | шторм скриптов: IP вебчата (`x-real-ip` — платформа, не подделать), chatId Telegram                                     | `bot/rate-limit.ts`         |
  | `max_tokens` (дефолт 1024) | простыни-ответы, раздувающие и квоту, и промт следующих запросов                                                        | `bot/llm.ts`                |
  | капы записи истории        | раздутые ключи в Redis (20 сообщений × 4000 символов)                                                                   | `bot/store.ts`              |

  Все проверки стоят до парсинга тела / походов в Redis-LLM; лимитер fail-open
  (мёртвый Redis не блокирует чат), пороги — env (`RATE_LIMIT_*`, `LLM_MAX_TOKENS`,
  окно истории `HISTORY_WINDOW`, порог dumb-ответа `DUMB_SCORE_THRESHOLD`,
  TTL `HISTORY_TTL_SECONDS`/`TELEGRAM_SEEN_TTL_SECONDS` — слайсы в `bot/config.ts`).
  Остаточный риск: джейлбрейки промта и распределённая атака с пулом IP — против
  первой контент публичный (риск принят), против второй — Turnstile при необходимости.

## Локальная разработка

`vercel dev` на этой машине не годится: после включения Windows Developer Mode он
стартует, но dev-роутер не доводит rewrites до функции (см. «Грабли платформы»),
поэтому функцию поднимает dev-адаптер:

```bash
npm run dev:function   # node:http на 3000: tsc api/bot.ts + bot/ + контент + .env.local
npm run dev            # vite (5173), /api проксируется на 3000
```

Подробности и одноразовая симуляция рантайма — [local-dev.md](local-dev.md).

## Грабли платформы (проверено на практике)

- **Сборка артефакта функции.** Билдер `@vercel/node` компилирует TS→JS
  (typescript + babel) и трейсит граф импортов (`@vercel/nft`, node-file-trace)
  в артефакт функции. Это не склейка в один js-файл: артефакт — набор модулей,
  рантайм грузит их нативным Node-лоадером (отсюда следующий пункт).
- **ESM-расширения.** Проект собран как `"type": "module"` — относительные импорты
  в `api/` и `bot/` обязаны иметь расширение `.js`. Vercel запускает функцию нативным
  Node-лоадером: без расширения — `ERR_MODULE_NOT_FOUND` и 500 на любом запросе,
  включая GET. Локально vite/vitest/tsc расширение прощают, так что прод-падение
  ловится только симуляцией рантайма (см. local-dev.md) или деплоем.
- **Файлы попадают в артефакт только через литеральный путь.** Трейсер затрейсит
  fs-чтение, только если путь — литерал относительно импортирующего модуля:

  | Паттерн                                                              | Трейсится |
  | -------------------------------------------------------------------- | --------- |
  | `readFileSync(new URL("./x.md", import.meta.url), "utf8")` — литерал | да        |
  | массив литеральных `new URL(...)` + `map(readFileSync)`              | да        |
  | путь собран через промежуточные переменные                           | нет       |
  | путь из `process.env` / параметров рантайма                          | нет       |

  `readdirSync` и glob-листинги не трейсятся: файлы, не упомянутые литералом,
  в артефакт не уедут — локально такой код работает, в облаке даст `ENOENT`.
  Деградация мягкая: недоступный `knowledge.json` → `knowledge.load()` отдаёт
  null, UI-ветки продолжают работать (пустые чипсы, /start без кнопок), чат
  отвечает безопасным текстом; недоступный md-раздел → сборка промта бросает
  с точной причиной, brain логирует «system-промт не собран» и уходит в
  dumb-режим, не вызывая LLM (ошибка контента не маскируется под «LLM
  недоступен»). В обоих случаях причина видна в логах (`[knowledge]` /
  `[brain]`). JSON-импорт с `with { type: "json" }`
  не нужен: `knowledge.json` читается fs-литералом в `knowledge.ts` +
  `JSON.parse`, md-разделы — литералами в `prompt.ts`. Статику `dist/`
  функция не видит (она на CDN, не в лямбде).

- **Rewrites не меняют pathname.** Rewrite меняет доставку, а не URL: функция
  видит исходный pathname (`/api/chat`, а не `/api/bot`) — иначе switch в
  `api/bot.ts` не работал бы. Тело запроса, заголовки (в т.ч. secret-token) и
  query проходят без изменений. Явный список rewrites (а не catch-all
  `/api/(.*)`): мусорные `/api/*` умирают платформенным 404 — функция не
  вызывается и не будит холодный инстанс.
- **Превью-деплои и вебхук.** Пуш в ветку (не `main`) по умолчанию создаёт
  preview-деплой: commit-URL (новый на каждый пуш) + стабильный branch-URL
  `<project>-git-<branch>-<scope>.vercel.app`; превью отдают `noindex`,
  кастомный домен к ним сам не привязывается. Отключить: Settings → Build and
  Deployment → Ignored Build Step → «Only build production». Telegram-вебхук
  один на бота: тест бота на preview-URL через `/api/telegram-setup` перекидывает
  вебхук с прода — после теста вернуть назад.
- **Env запекается в деплой.** Изменение переменных в дашборде или через CLI не
  влияет на уже задеплоенную функцию — после правок нужен Redeploy (Deployments →
  ⋯ → Redeploy; пустые коммиты для этого не нужны). `.env.local` наверх не
  синхронизируется: значения задаются `vercel env add` или дашбордом, а
  `vercel env pull` направление ровно одно — из облака, с перезаписью файла.
- **TS2688 в логах сборки** (`Cannot find type definition file for 'node'`) — шум
  транслятора @vercel/node: он запускает tsc из своего рабочего каталога, где
  `"types": ["node"]` из tsconfig не резолвится. Шаг transpile-only — на деплой
  и рантайм не влияет, чинить не нужно.
- **`vercel dev` и виртуальные диски** (RAM-диск ImDisk, subst): CLI зовёт
  `fs.realpath.native` (`GetFinalPathNameByHandle`), который на таких томах падает
  с `EISDIR` на любом пути — репо на виртуальном диске локальный dev-режим CLI
  ломает, на физическом всё работает. На деплой-цепочку не влияет; остальной
  тулчейн (vite/tsc/vitest/git) native realpath не зовёт. Детали — local-dev.md.
- **`vercel build`/`vercel dev` на Windows: `EPERM: symlink`.** CLI в
  неэлевированном процессе не создаёт symlinks в кэше билдеров (`builders-vlt`),
  если выключен Windows Developer Mode. Лечение: включить Developer Mode
  (Параметры → Для разработчиков) или элевировать терминал. Повседневная замена —
  dev-адаптер `npm run dev:function` (см. local-dev.md).
- **`vercel dev` (v65, framework-режим) не применяет rewrites к функциям.**
  Dev-роутер зовёт функцию, только если путь совпадает с файлом в `api/`
  (`/api/bot`); путь, попадающий в функцию через rewrite (`/api/chat`),
  уходит в заспавненный framework-сервер (vite). Прокси автономного vite
  (`/api → 127.0.0.1:3000`) при этом замыкает петлю vercel → vite → vercel:
  заголовки `x-vercel-*` растут с каждым кругом — GET умирает с 431, POST
  с телом роняет CLI (`read ECONNRESET`). Поэтому прокси в `vite.config.ts`
  включается только вне vercel dev (детектор — env `PORT`). Проверено
  2026-11 на v65.10.0 и v65.11.0 (на тот момент latest); локальная замена —
  dev-адаптер (см. local-dev.md).

## Ограничения и развитие

- История диалога — последние 10 сообщений, без суммаризации; записи одного чата
  гонками не защищены (last-write-wins) — для визитки осознанный компромисс.
- dumb-поиск — морфология, IDF и синонимы `keywords` (bot/brain/search.ts),
  без векторного поиска — осознанный минимум для объёма справки; подсказки
  следующего вопроса показываются только в dumb-fallback.
- Идеи на будущее: правка промта/справки без деплоя (Blob/KV-хранилище),
  векторный поиск по справке, rate-limit на `/api/chat`.
- Разделение «лога» и «журнала деградаций»: сейчас модули собирают warn-строки
  сами — факт деградации и его формулировка склеены в одну шаблонную строку
  (образец: `errorBody` в redis-rest.ts). В serverless лог остаётся единственным
  каналом к оператору, поэтому честнее развести ЧТО (структурное событие:
  статус, сниппет тела, отвалившаяся функция) и КАК (форматирование — в log.ts),
  а тесты транспорта пиннить фактом вызова с полями, не строкой.
