# Архитектура

> Как всем этим пользоваться и чинить — мануал владельца в [manual.md](manual.md).

## Общая схема

```
Браузер (статика: Vite MPA, dist/)                    Telegram
   │  POST /api/chat {sessionId, text}                   │  POST /api/telegram (update)
   ▼                                                     ▼
        ┌──────────────── vercel.json (rewrites) ────────────────┐
        │            /api/chat  ─┐            /api/telegram ─┐   │
        └────────────────────────┼───────────────────────────┼───┘
                                 ▼                           ▼
                     ┌───────────────────────────────────────────┐
                     │        api/bot.ts — ОДНА функция          │
                     │        роутер по pathname                 │
                     └──────────────┬────────────────────────────┘
                                    ▼
                     bot/http/webchat.ts        bot/http/telegram-webhook.ts
                             └──────┬──────┘
                     bot/store.ts — история диалога в Upstash Redis
                        (REST; недоступен → stateless, fail-open)
                                    ▼
                            bot/brain/brain.ts — answer()
                        LLM (OpenAI-совместимый API)
                                   ↘ при ошибке/таймауте
                        dumb-поиск по bot/brain/knowledge.json
```

Третий rewrite ведёт в ту же функцию админ-маршрут `/api/telegram-setup`
(диагностика, вебхук, просмотр промта) — описан ниже.

## Почему одна функция, а не две

Файлы в корневом `api/` Vercel деплоит как отдельные функции. Свежая рекомендация
документации Vercel: держать связанные маршруты в **одной общей функции** — тогда
Fluid compute переиспользует один инстанс для всех источников (меньше холодных
стартов), в дашборде один объект, и общий код `brain`/`store` грузится один раз.

Чтобы URL остались семантичными (`/api/chat`, `/api/telegram`, `/api/telegram-setup`),
в `vercel.json` настроены rewrites на `/api/bot`. Это единственный `vercel.json` в
проекте — Vite детектится и собирается сам (`vite build` → `dist/`).

Сигнатура функции — современный Web-стандарт (рекомендация Vercel):

```ts
export default {
  async fetch(request: Request): Promise<Response> { … }
};
```

## Контент и промт — bot/brain/knowledge.json + bot/brain/prompts/*.md

Справка («мозг» бота) живёт в данных, не в коде:

- `bot/brain/knowledge.json` — массив `{title, text}`, источник истины для справки.
  Потребляют его трое: dumb-поиск (brain), чипсы вебчата (GET `/api/chat`) и
  inline-кнопки Telegram (`/start`) — везде берутся первые 3 заголовка.
- `bot/brain/prompts/00-persona.md`, `10-rules.md`, `20-knowledge.md` — разделы system
  prompt готовым текстом, без парсинга; единственная обработка — `trim()` и
  строковая подстановка плейсхолдера `{{KNOWLEDGE}}` в 20-knowledge.
- `bot/brain/prompt.ts` — сборщик: `systemPrompt()` склеивает md-разделы и вставляет
  справку, `knowledgeEntries()` отдаёт JSON. Чтение — `readFileSync` с
  литеральным `new URL(...)` относительно модуля: только такие пути nodeFileTrace
  затрейсит в артефакт функции (таблица — в «Граблях платформы»). Результат
  кэшируется на тёплый инстанс (`cached ??=`) — чтение с диска лямбды один раз,
  не на каждый запрос.

Контент вшивается в артефакт на деплое (как и env): правка справки или промта =
пуш → деплой → оба канала отвечают по-новому.

## Память диалога — bot/store.ts

- Upstash Redis по REST API, чистый `fetch` без SDK (REST-эндпоинт один,
  зависимости не нужны): команда — JSON-массив в теле POST, таймаут 5 с.
- Ключи: `chat:web:{sessionId}` (вебчат) и `chat:tg:{chatId}` (Telegram). История —
  одно значение: JSON-массив `{role, content}`, читается и пишется целиком одним
  SET (атомарно; гонки concurrent-запросов одного чата для визитки не критичны —
  last-write-wins).
- TTL 24 часа, обновляется при каждой записи — «скользящее окно» активности. В
  промт идёт последние 10 сообщений (`HISTORY_WINDOW` в `bot/brain/brain.ts`).
- **Fail-open.** Любая проблема — нет env, сеть, не-200, ошибка в ответе, битый
  JSON — даёт пустую историю и `console.warn`, запрос не падает: бот обязан
  отвечать и без Redis, в stateless-режиме (контекст — только текущий вопрос).
- `/reset` (Telegram) удаляет ключ; «новый диалог» вебчата — новый sessionId
  (старый ключ истечёт по TTL сам).

## Вебчат — bot/http/webchat.ts + src/chat/

- Клиент шлёт только `{sessionId, text}`. sessionId генерирует
  `crypto.randomUUID()` и хранит в localStorage — контекст переживает
  перезагрузку страницы; сам транскрипт — в памяти виджета.
- Сервер: история из Redis → `answer(question, history)` → пара вопрос/ответ
  обратно в историю → `{ok, text, mode}`.
- `GET /api/chat` — `{ok, service, chips}`: первые 3 заголовка справки (чипсы
  развёрнутого виджета).
- Валидация: sessionId — белый список `[A-Za-z0-9_-]{8,64}` (он часть ключа
  Redis), text — непустая строка до 2000 символов.
- `src/chat/chat-widget.ts` — UI: плавающая кнопка, панель, индикатор
  «печатает…», бейдж «офлайн-справка» для `mode=dumb`. Никакого innerHTML с
  данными пользователя — только `textContent`.

## Telegram — bot/http/telegram-webhook.ts + bot/telegram-api.ts

- Webhook принимает только POST с заголовком `X-Telegram-Bot-Api-Secret-Token`,
  равным `TELEGRAM_WEBHOOK_SECRET` (секрет задаётся при setWebhook). Иначе — 401:
  чужие запросы не тратят вызовы LLM.
- Свободный текст и нажатая inline-кнопка идут одним потоком: история из Redis →
  `answer()` → пара вопрос/ответ в историю → `sendMessage`. Команды (`/start`,
  `/help`, `/reset`, `/about`) в историю не пишутся — это действия интерфейса,
  а не реплики диалога.
- `/start` — приветствие + inline-кнопки (первые 3 заголовка справки). Кнопка
  несёт `callback_data = "ask:{n}"` — лимит Telegram 64 байта на callback_data,
  вопрос восстанавливается из справки по индексу. `answerCallbackQuery` гасит
  спиннер сразу, не дожидаясь LLM; `editMessageText` снимает одноразовую
  клавиатуру со старого сообщения.
- `/about` — элемент справки с заголовком «Кто я»; заголовок может переименовать
  сам владелец (контент правится без правки кода), поэтому fallback — первый
  элемент.
- `sendMessage` режет ответы длиннее 4096 символов (лимит Telegram на одно
  сообщение) — по последнему переводу строки в окне.
- Ошибки отправки/LLM ловятся, наружу всегда отдаётся 200 (иначе Telegram будет
  повторять доставку update). Сообщения без текста (фото, стикеры) грациозно
  игнорируются.
- `bot/telegram-api.ts` — тонкая обёртка Bot API на `fetch`, без зависимостей:
  `sendMessage`, `editMessageText`, `answerCallbackQuery`, `setWebhook`,
  `getWebhookInfo`.

## Админ-маршрут — /api/telegram-setup (bot/http/telegram-admin.ts)

Один путь (третий rewrite), ветвление по query-параметру `section` — подпути
через `vercel.json` не заводим. Зачем: регистрация вебхука без прямого доступа к
api.telegram.org (у части провайдеров заблокирован), health бота и просмотр
собранного промта. Защищён тем же секрет-заголовком, что и вебхук; без секрета —
404 (маршрут скрыт).

| Запрос                | Ответ                                                                                                                                  |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| GET `?section=health` | `{llm, redis, telegram}` — `pingLlm()` + `store.ping()` + `getWebhookInfo()`, параллельно; ошибка одного пункта не влияет на остальные |
| GET `?section=prompt` | собранный `systemPrompt()` целиком (секрет есть — справка не отдельная сущность)                                                       |
| GET без section       | `getWebhookInfo` — историческое поведение                                                                                              |
| POST                  | `setWebhook`: `url` из origin запроса, `secret_token` из env, `allowed_updates: ["message", "callback_query"]`                         |
| прочие методы         | 405                                                                                                                                    |

## Безопасность

- Секреты живут только в env (Vercel) и `.env.local` (в `.gitignore`). На фронте
  секретов нет вообще — `/api/chat` публичный по дизайну (это справка).
- Webhook защищён secret-заголовком; без валидного секрета — 401. Админ-маршрут —
  тем же секретом, но без валидного секрета отвечает 404 (не подтверждает
  существование маршрута).
- Валидация входа: sessionId-паттерн (он часть ключа Redis), длина текста,
  роли сообщений — защита от мусорных запросов и произвольных ключей.
- CORS не настраивается: сайт и `/api` на одном домене (same-origin).

## Локальная разработка

`vercel dev` на этой машине сломан (`EPERM: symlink`, см. «Грабли платформы»),
поэтому функцию поднимает dev-адаптер:

```bash
npm run dev:function   # node:http на 3000: tsc api/ + копия контента + .env.local
npm run dev            # vite (5173), /api проксируется на 3000
```

Подробности и одноразовая симуляция рантайма — [local-dev.md](local-dev.md).

## Грабли платформы (проверено на практике)

- **Сборка артефакта функции.** Билдер `@vercel/node` компилирует TS→JS
  (typescript + babel) и трейсит граф импортов (`@vercel/nft`, node-file-trace)
  в артефакт функции. Это не склейка в один js-файл: артефакт — набор модулей,
  рантайм грузит их нативным Node-лоадером (отсюда следующий пункт).
- **ESM-расширения.** Проект собран как `"type": "module"` — относительные импорты
  в `api/` и `bot/` обязаны иметь расширение `.js`. Vercel запускает функцию нативным
  Node-лоадером: без расширения — `ERR_MODULE_NOT_FOUND` и 500 на любом запросе,
  включая GET. Локально vite/vitest/tsc расширение прощают, так что прод-падение
  ловится только симуляцией рантайма (см. local-dev.md) или деплоем.
- **Файлы попадают в артефакт только через литеральный путь.** Трейсер затрейсит
  fs-чтение, только если путь — литерал относительно импортирующего модуля:

  | Паттерн                                                              | Трейсится |
  | -------------------------------------------------------------------- | --------- |
  | `readFileSync(new URL("./x.md", import.meta.url), "utf8")` — литерал | да        |
  | массив литеральных `new URL(...)` + `map(readFileSync)`              | да        |
  | путь собран через промежуточные переменные                           | нет       |
  | путь из `process.env` / параметров рантайма                          | нет       |

  `readdirSync` и glob-листинги не трейсятся: файлы, не упомянутые литералом,
  в артефакт не уедут — локально такой код работает, в облаке даст `ENOENT`
  (промт-сборщик на этот случай падает внутри `askLlm` → ответ уходит в
  dumb-режим, в логах виден `ENOENT`). JSON-импорт с `with { type: "json" }` не
  нужен: `knowledge.json` читается fs-литералом + `JSON.parse`. Статику `dist/`
  функция не видит (она на CDN, не в лямбде).

- **Rewrites не меняют pathname.** Rewrite меняет доставку, а не URL: функция
  видит исходный pathname (`/api/chat`, а не `/api/bot`) — иначе switch в
  `api/bot.ts` не работал бы. Тело запроса, заголовки (в т.ч. secret-token) и
  query проходят без изменений. Явный список rewrites (а не catch-all
  `/api/(.*)`): мусорные `/api/*` умирают платформенным 404 — функция не
  вызывается и не будит холодный инстанс.
- **Превью-деплои и вебхук.** Пуш в ветку (не `main`) по умолчанию создаёт
  preview-деплой: commit-URL (новый на каждый пуш) + стабильный branch-URL
  `<project>-git-<branch>-<scope>.vercel.app`; превью отдают `noindex`,
  кастомный домен к ним сам не привязывается. Отключить: Settings → Build and
  Deployment → Ignored Build Step → «Only build production». Telegram-вебхук
  один на бота: тест бота на preview-URL через `/api/telegram-setup` перекидывает
  вебхук с прода — после теста вернуть назад.
- **Env запекается в деплой.** Изменение переменных в дашборде или через CLI не
  влияет на уже задеплоенную функцию — после правок нужен Redeploy (Deployments →
  ⋯ → Redeploy; пустые коммиты для этого не нужны). `.env.local` наверх не
  синхронизируется: значения задаются `vercel env add` или дашбордом, а
  `vercel env pull` направление ровно одно — из облака, с перезаписью файла.
- **TS2688 в логах сборки** (`Cannot find type definition file for 'node'`) — шум
  транслятора @vercel/node: он запускает tsc из своего рабочего каталога, где
  `"types": ["node"]` из tsconfig не резолвится. Шаг transpile-only — на деплой
  и рантайм не влияет, чинить не нужно.
- **`vercel dev` и виртуальные диски** (RAM-диск ImDisk, subst): CLI зовёт
  `fs.realpath.native` (`GetFinalPathNameByHandle`), который на таких томах падает
  с `EISDIR` на любом пути — репо на виртуальном диске локальный dev-режим CLI
  ломает, на физическом всё работает. На деплой-цепочку не влияет; остальной
  тулчейн (vite/tsc/vitest/git) native realpath не зовёт. Детали — local-dev.md.
- **`vercel build`/`vercel dev` на Windows: `EPERM: symlink`.** CLI в
  неэлевированном процессе не создаёт symlinks в кэше билдеров (`builders-vlt`),
  если выключен Windows Developer Mode. Лечение: включить Developer Mode
  (Параметры → Для разработчиков) или элевировать терминал. Повседневная замена —
  dev-адаптер `npm run dev:function` (см. local-dev.md).
- **`vercel dev` (v65, framework-режим) не применяет rewrites к функциям.**
  Dev-роутер зовёт функцию, только если путь совпадает с файлом в `api/`
  (`/api/bot`); путь, попадающий в функцию через rewrite (`/api/chat`),
  уходит в заспавненный framework-сервер (vite). Прокси автономного vite
  (`/api → 127.0.0.1:3000`) при этом замыкает петлю vercel → vite → vercel:
  заголовки `x-vercel-*` растут с каждым кругом — GET умирает с 431, POST
  с телом роняет CLI (`read ECONNRESET`). Поэтому прокси в `vite.config.ts`
  включается только вне vercel dev (детектор — env `PORT`). Проверено
  2026-11 на v65.10.0 и v65.11.0 (на тот момент latest); локальная замена —
  dev-адаптер (см. local-dev.md).

## Ограничения и развитие

- История диалога — последние 10 сообщений, без суммаризации; записи одного чата
  гонками не защищены (last-write-wins) — для визитки осознанный компромисс.
- dumb-режим ищет по словам, без морфологии и синонимов — это осознанный минимум.
- Идеи на будущее: правка промта/справки без деплоя (Blob/KV-хранилище),
  векторный поиск по справке, rate-limit на `/api/chat`.
